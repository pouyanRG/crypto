# ۳. ساختار اصلی Layout

## ۳.۱ Root Layout

فایل اصلی layout پروژه باید ساختار مشترک کل برنامه را کنترل کند.

در حال حاضر فایل `layout.jsx` فقط `Providers` و `children` را render می‌کند. در فاز ۴ باید Header و Footer نیز در همین سطح یا در یک shell مشترک قرار بگیرند.

ساختار منطقی مورد انتظار:

```jsx
<body>
  <Providers>
    <div className="app-shell">
      <Header />

      <main className="app-content">
        {children}
      </main>

      <Footer />
    </div>
  </Providers>
</body>
```

### وظایف Root Layout

Root Layout باید:

- `lang="en"` داشته باشد.
- `dir="ltr"` داشته باشد.
- فونت اصلی را تنظیم کند.
- Design Tokenها را وارد کند.
- Theme Provider را فعال نگه دارد.
- پس‌زمینه‌ی اصلی برنامه را اعمال کند.
- Header را در تمام صفحات نمایش دهد.
- Footer را در تمام صفحات نمایش دهد.
- حداقل ارتفاع صفحه را حفظ کند.
- محتوای اصلی را بین Header و Footer قرار دهد.
- از تکرار wrapperها در صفحات جلوگیری کند.

### رفتار ارتفاع صفحه

اگر محتوای یک route کم باشد، Footer نباید وسط صفحه شناور باشد. ساختار باید طوری باشد که:

```css
body {
  min-height: 100vh;
}

.app-shell {
  min-height: 100vh;
  display: flex;
  flex-direction: column;
}

.app-content {
  flex: 1;
}
```

در نتیجه:

- Header بالای صفحه می‌ماند.
- محتوای صفحه فضای اصلی را می‌گیرد.
- Footer پایین صفحه قرار می‌گیرد.
- در صفحات بلند، Footer بعد از محتوا قرار می‌گیرد.

# ۴. Header

کامپوننت Header در `Header.jsx` قرار دارد و باید به پوسته‌ی اصلی متصل و کامل شود.

## ۴.۱ اجزای Header

Header باید شامل بخش‌های زیر باشد:

### Logo یا Brand

برند پروژه باید شامل موارد زیر باشد:

- آیکون یا نشان کوچک
- نام پروژه
- لینک به Dashboard یا `/`

با کلیک روی برند، کاربر باید به صفحه‌ی اصلی برگردد.

### Navigation

Navigation باید به routeهای اصلی دسترسی بدهد:

- Dashboard
- Markets
- Watchlist
- Portfolio
- Compare

طبق مشخصات رسمی، این پنج بخش باید در navigation وجود داشته باشند.

### Theme Switcher

Header باید کنترل تغییر تم داشته باشد:

- Dark mode
- Light mode

این کنترل باید از Zustand استفاده کند و مستقیماً منطق جداگانه برای نگهداری theme نسازد.

### Data Source Status

Header یا بخشی از shell باید وضعیت منبع داده را نشان دهد، برای مثال:

- Live
- Updating
- Cached
- Offline
- API unavailable

این وضعیت نباید ادعا کند داده live است، مگر اینکه واقعاً آخرین درخواست با موفقیت انجام شده باشد.

### کنترل‌های احتمالی آینده

در این فاز می‌توان جای مناسب برای موارد زیر را در نظر گرفت، اما پیاده‌سازی کامل آن‌ها الزامی نیست:

- Refresh data
- User preference menu
- آخرین زمان به‌روزرسانی
- واحد پول انتخاب‌شده
- وضعیت اتصال

این موارد نباید باعث شوند scope فاز ۴ به فازهای بعدی کشیده شود.

# ۵. Navigation

کامپوننت فعلی `Nav.jsx` از `usePathname` برای تشخیص route فعال استفاده می‌کند. این رفتار باید در فاز ۴ کامل و پایدار شود.

## ۵.۱ لینک‌های الزامی

Navigation باید لینک‌های زیر را داشته باشد:

| عنوان | مسیر |
|---|---|
| Dashboard | `/` |
| Markets | `/market` |
| Watchlist | `/watchlist` |
| Portfolio | `/portfolio` |
| Compare | `/compare` |

در وضعیت فعلی، لینک Portfolio در Nav وجود ندارد و باید در فاز ۴ اضافه شود.

## ۵.۲ تشخیص route فعال

هر route فعال باید حالت بصری مشخصی داشته باشد:

- background متفاوت
- رنگ accent
- focus واضح
- حفظ خوانایی در Dark و Light mode

برای Dashboard باید فقط در مسیر دقیق `/` فعال شود. نباید هنگام رفتن به `/market` یا `/coin/bitcoin`، Dashboard به‌اشتباه active بماند.

برای routeهای زیرصفحه‌ای باید از prefix مناسب استفاده شود:

```text
/market
/market/...
```

اما منطق active شدن باید با دقت نوشته شود تا مسیرهای مشابه اشتباه تشخیص داده نشوند.

## ۵.۳ Navigation در موبایل

در صفحه‌ی کوچک، تمام لینک‌ها نباید باعث شکستن layout شوند.

راهکارهای قابل قبول:

- horizontal scroll
- منوی جمع‌شونده
- bottom navigation محدود
- نمایش لینک‌ها در چند ردیف کنترل‌شده

برای این پروژه، چون تعداد لینک‌ها کم است، horizontal scroll یا navigation فشرده می‌تواند کافی باشد؛ اما باید بررسی شود که:

- متن لینک‌ها بریده نشود.
- Header ارتفاع غیرمنطقی پیدا نکند.
- لینک فعال قابل مشاهده باشد.
- کاربر بتواند با touch و keyboard حرکت کند.

## ۵.۴ accessibility در Navigation

Navigation باید:

- داخل عنصر `<nav>` باشد.
- در صورت نیاز `aria-label="Primary navigation"` داشته باشد.
- لینک واقعی `<a>` یا `next/link` باشد.
- با Tab قابل دسترسی باشد.
- focus ring واضح داشته باشد.
- فقط با رنگ، active بودن را نشان ندهد.
- ترتیب keyboard منطقی داشته باشد.

# ۶. Theme Switcher

Theme switcher یکی از بخش‌های اصلی فاز ۴ است.

## ۶.۱ تم‌های پشتیبانی‌شده

دو تم باید وجود داشته باشد:

- Dark
- Light

Dark mode حالت پیش‌فرض پروژه است.

در حال حاضر tokenهای هر دو تم در `tokens.css` وجود دارند و `ThemeProvider` در `providers.tsx` مقدار `data-theme` را روی عنصر `html` قرار می‌دهد.

پس بخش زیرساختی theme تا حد زیادی آماده است، اما کنترل قابل استفاده برای کاربر در Header باید ساخته یا تکمیل شود.

## ۶.۲ رفتار Theme Switcher

با تغییر theme:

1. کاربر روی کنترل کلیک می‌کند.
2. مقدار theme در Zustand تغییر می‌کند.
3. مقدار `data-theme` روی `<html>` تغییر می‌کند.
4. رنگ‌های tokenها به‌صورت خودکار عوض می‌شوند.
5. Header، Footer، کارت‌ها، جدول‌ها و صفحات باید با تم جدید سازگار شوند.
6. ترجیح کاربر باید در `localStorage` باقی بماند.

## ۶.۳ وضعیت اولیه

در اولین ورود کاربر:

- اگر theme ذخیره‌شده وجود دارد، همان استفاده شود.
- اگر داده خراب باشد، مقدار معتبر نادیده گرفته شود.
- اگر theme ذخیره نشده باشد، Dark mode فعال باشد.
- تغییر theme نباید باعث crash یا hydration error شود.

## ۶.۴ جلوگیری از Flash

یکی از مشکلات مهم theme، نمایش لحظه‌ای تم اشتباه در زمان بارگذاری است.

مثلاً:

1. HTML ابتدا با Dark mode نمایش داده می‌شود.
2. بعد JavaScript اجرا می‌شود.
3. theme ذخیره‌شده Light است.
4. صفحه برای لحظه‌ای Dark دیده می‌شود و سپس Light می‌شود.

در فاز ۴ باید این رفتار تا حد ممکن بررسی و کنترل شود. راهکار می‌تواند شامل این موارد باشد:

- مقدار پیش‌فرض مناسب
- اعمال زودهنگام theme
- جلوگیری از نمایش کنترل theme قبل از hydrate شدن
- استفاده از ساختار فعلی Zustand و بررسی رفتار SSR/CSR

هدف این است که تغییر theme از نظر بصری ناگهانی و آزاردهنده نباشد.

## ۶.۵ accessibility در Theme Switcher

اگر کنترل فقط آیکون دارد، باید حتماً داشته باشد:

```jsx
<button
  type="button"
  aria-label="Switch to light theme"
>
  ...
</button>
```

همچنین بهتر است:

- tooltip یا عنوان مناسب داشته باشد.
- حالت فعلی را برای screen reader مشخص کند.
- با Enter و Space کار کند.
- در focus حالت واضح داشته باشد.
- در حالت disabled احتمالی رفتار صحیح داشته باشد.

# ۷. Responsive Shell

فاز ۴ باید shell را برای اندازه‌های مختلف صفحه آماده کند.

## ۷.۱ دسکتاپ

در دسکتاپ:

- Header در عرض مناسب قرار بگیرد.
- محتوای اصلی max-width داشته باشد.
- navigation در یک ردیف قابل مشاهده باشد.
- فاصله‌ی کناری مناسب باشد.
- Footer تمام عرض صفحه را پوشش دهد.
- shell به اندازه‌ی کافی فشرده و مناسب ابزار تحلیلی باشد.

## ۷.۲ تبلت

در تبلت:

- فاصله‌های افقی کاهش پیدا کنند.
- navigation همچنان قابل استفاده بماند.
- محتوای اصلی از لبه‌های viewport فاصله داشته باشد.
- Header دچار فشردگی بیش از حد نشود.

## ۷.۳ موبایل

در موبایل:

- Header نباید باعث overflow افقی کل صفحه شود.
- لوگو و navigation باید فضای کافی داشته باشند.
- متن برند نباید روی لینک‌ها بیفتد.
- routeها باید قابل لمس باشند.
- Footer نباید متن‌هایش را بیرون بزند.
- paddingها باید کاهش پیدا کنند.
- محتوا باید از لبه‌ی صفحه فاصله داشته باشد.
- focus و tap targetها باید قابل استفاده باشند.

حداقل اندازه‌ی قابل قبول برای کنترل‌های لمسی باید رعایت شود؛ به‌طور معمول حدود ۴۴ پیکسل برای target لمسی مناسب است.

## ۷.۴ max-width

محتوا نباید در مانیتورهای بسیار بزرگ بیش از حد کشیده شود. بهتر است shell یک container مشخص داشته باشد، مانند:

```text
max-width: 1200px
```

مقدار نهایی باید با design direction پروژه هماهنگ باشد.

در کد فعلی `max-w-6xl` استفاده شده است که می‌تواند پایه‌ی مناسبی باشد، ولی باید در صفحات واقعی نیز بررسی شود.

## ۷.۵ فاصله‌ی مشترک صفحات

فاز ۴ باید برای محتوای routeها فاصله‌ی مشترک تعریف کند:

- فاصله از Header
- padding افقی
- فاصله‌ی عمودی بخش‌ها
- فاصله‌ی مناسب در موبایل

مثلاً:

```jsx
<main className="mx-auto w-full max-w-6xl flex-1 px-4 py-6 sm:px-6 lg:py-8">
  {children}
</main>
```

این کار باعث می‌شود هر صفحه مجبور نباشد container مخصوص خودش را بسازد.

# ۸. Footer

Footer در `Footer.jsx` وجود دارد و باید بخشی از layout مشترک شود.

## ۸.۱ محتوای Footer

Footer حداقل باید شامل attribution به CoinGecko باشد:

```text
Powered by CoinGecko API
```

لینک باید:

- به صفحه‌ی رسمی CoinGecko یا API آن برود.
- در صورت باز شدن تب جدید، `rel="noreferrer"` یا تنظیم مناسب داشته باشد.
- در Light و Dark mode خوانا باشد.
- focus state داشته باشد.

## ۸.۲ نقش Footer

Footer در این فاز نباید تبدیل به صفحه‌ی جداگانه یا بخش تبلیغاتی بزرگ شود. نقش آن محدود و کاربردی است:

- attribution
- اطلاعات کوتاه پروژه
- لینک‌های ضروری در صورت نیاز
- نمایش سال یا نسخه در صورت تصمیم پروژه

## ۸.۳ Responsive Footer

Footer باید در موبایل:

- متن را wrap کند.
- از viewport بیرون نزند.
- لینک‌ها روی هم نیفتند.
- فاصله‌ی کافی از پایین صفحه داشته باشد.

# ۹. Metadata پایه و Route Metadata

فاز ۴ شامل metadata پایه برای برنامه و routeهاست.

## ۹.۱ Metadata عمومی

در Root Layout باید موارد زیر وجود داشته باشد:

- title پیش‌فرض
- title template
- description
- زبان صفحه
- theme color در صورت نیاز
- viewport مناسب
- favicon
- metadata مربوط به Open Graph در صورت scope پروژه

در حال حاضر title و description پایه در `layout.jsx` وجود دارد و باید بررسی شود که با عنوان نهایی محصول هماهنگ باشد.

## ۹.۲ عنوان routeها

هر صفحه باید عنوان قابل فهم داشته باشد:

| Route | عنوان پیشنهادی |
|---|---|
| `/` | Dashboard |
| `/market` | Markets |
| `/coin/[id]` | Coin Detail |
| `/watchlist` | Watchlist |
| `/portfolio` | Portfolio |
| `/compare` | Compare |

با `title.template` می‌توان خروجی‌هایی مانند زیر داشت:

```text
Markets | Crypto Analytics Dashboard
```

## ۹.۳ Metadata داینامیک Coin Detail

برای `/coin/[id]`، در صورت فراهم بودن داده، عنوان می‌تواند شامل نام کوین باشد:

```text
Bitcoin | Crypto Analytics Dashboard
```

اما اگر دریافت داده شکست خورد، باید title fallback وجود داشته باشد و metadata داینامیک باعث خطای صفحه نشود.

## ۹.۴ Favicon و Brand

فاز ۴ باید بررسی کند:

- favicon وجود دارد یا نه.
- favicon با برند پروژه هماهنگ است یا نه.
- صفحه‌ی browser tab عنوان درست نشان می‌دهد یا نه.
- metadata با مسیر فعلی همخوانی دارد یا نه.

# ۱۰. وضعیت منبع داده

در مشخصات پروژه Header باید «وضعیت منبع داده» را نمایش دهد.

این به معنی ساخت سیستم کامل مانیتورینگ API نیست. در فاز ۴ فقط باید محل و قرارداد نمایشی این وضعیت مشخص شود.

## حالت‌های احتمالی

### Live

آخرین درخواست با موفقیت انجام شده و داده‌ی فعلی دریافت شده است.

### Updating

درخواست جدید در حال اجراست.

### Cached

داده از cache نمایش داده می‌شود و الزاماً تازه‌ترین پاسخ نیست.

### Offline

اتصال شبکه موجود نیست یا برنامه در حالت محدود آفلاین است.

### Unavailable

API پاسخ معتبر نداده یا خطا رخ داده است.

## نکته‌ی مهم

نباید صرفاً یک Badge با متن `Live` ساخته شود که همیشه Live باقی بماند. این وضعیت باید در آینده قابل اتصال به TanStack Query باشد.

در فاز ۴ می‌توان:

- یک کامپوننت نمایشی قابل استفاده ساخت.
- props مناسب برای status تعریف کرد.
- آن را فعلاً با مقدار ثابت یا وضعیت محدود render کرد.
- اتصال کامل به query state را به فازهای داده یا Dashboard واگذار کرد.

# ۱۳. Accessibility فاز ۴

تمام پوسته‌ی مشترک باید اصول پایه‌ی دسترسی‌پذیری را رعایت کند.

## الزامات

- Header با عنصر `<header>`
- Navigation با عنصر `<nav>`
- محتوای اصلی با `<main>`
- Footer با `<footer>`
- لینک‌ها با `next/link`
- دکمه‌ها با `<button>`
- focus واضح
- ترتیب منطقی Tab
- label مناسب برای کنترل‌ها
- `aria-label` برای icon-only buttons
- عدم انتقال معنا فقط با رنگ
- کنتراست مناسب در هر دو theme
- عدم حذف outline بدون جایگزین
- امکان کار با keyboard

## Skip Link

در صورت نیاز بهتر است یک skip link اضافه شود:

```text
Skip to main content
```

این لینک به کاربران keyboard و screen reader اجازه می‌دهد از Navigation عبور کنند و مستقیماً به محتوای اصلی برسند.

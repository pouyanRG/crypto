# فاز ۳: Shared UI System

فاز ۳ مربوط به ساخت **سیستم کامپوننت‌های مشترک رابط کاربری** است؛ یعنی اجزایی که چندین صفحه و بخش پروژه از آن‌ها استفاده می‌کنند. هدف این فاز ساخت خود Dashboard، Markets یا Portfolio نیست، بلکه ایجاد پایه‌ی بصری و تعاملی یکپارچه برای همه‌ی آن صفحات است.

بر اساس `project-spec.md`، فاز ۳ شامل این موارد است:

- `Button`
- `Card`
- `Badge`
- `Tabs`
- `Table`
- `Input`
- `Select`
- `Skeleton`
- `Empty states`
- `Error states`
- رفتار صحیح keyboard و focus
- ویژگی‌های دسترسی‌پذیری مانند `aria-*`
- استفاده‌ی کامل از Design Tokens
- حذف hardcode رنگ، spacing، radius و typography

---

## ۱. هدف اصلی فاز ۳

در پایان این فاز، پروژه باید یک UI Kit داخلی و قابل‌استفاده‌مجدد داشته باشد.

به‌جای اینکه هر صفحه برای خودش دکمه، کارت، جدول یا پیام خطا بسازد، همه باید از کامپوننت‌های مشترک استفاده کنند.

مثلاً به‌جای:

```jsx
<button className="bg-blue-500 px-4 py-2">
  Save
</button>
```

باید چیزی شبیه این استفاده شود:

```jsx
<Button variant="primary">
  Save
</Button>
```

مزایای این کار:

- ظاهر تمام صفحات یکپارچه می‌شود.
- تغییر theme ساده‌تر می‌شود.
- حالت‌های loading، disabled و error در همه‌جا رفتار مشابه دارند.
- دسترسی‌پذیری یک‌بار درست پیاده‌سازی می‌شود.
- تکرار کد کاهش پیدا می‌کند.
- فازهای بعدی سریع‌تر ساخته می‌شوند.
- نگهداری پروژه ساده‌تر می‌شود.

---

# ۲. کامپوننت Button

`Button` یکی از مهم‌ترین primitiveهای سیستم UI است.

## حالت‌های لازم

حداقل باید این variantها را پشتیبانی کند:

### Primary

برای عملیات اصلی صفحه:

- Add to Watchlist
- Save
- Submit
- Add Asset

### Secondary یا Outline

برای عملیات ثانویه:

- Cancel
- Back
- View Details

### Ghost

برای دکمه‌های کم‌اهمیت یا کنترل‌های داخل Header و Toolbar:

- Theme switcher
- Refresh
- Close
- More options

### Destructive

برای عملیات خطرناک:

- Remove asset
- Clear watchlist
- Delete portfolio item

## اندازه‌ها

بهتر است Button اندازه‌های مشخص داشته باشد:

- `sm`
- `md`
- `lg`
- در صورت نیاز `icon`

اندازه‌ی دکمه نباید با تغییر متن یا loading دچار جابه‌جایی شدید شود.

## وضعیت‌های لازم

Button باید این stateها را داشته باشد:

- normal
- hover
- focus
- active
- disabled
- loading
- در صورت نیاز pressed

در حالت loading:

- کلیک مجدد نباید ممکن باشد.
- بهتر است spinner یا skeleton کوچک نمایش داده شود.
- متن یا layout دکمه نباید ناگهان جابه‌جا شود.

نمونه:

```jsx
<Button loading>
  Save
</Button>
```

## دسترسی‌پذیری Button

باید:

- عنصر واقعی `<button>` باشد.
- با Tab قابل دسترسی باشد.
- با Enter و Space فعال شود.
- در حالت disabled واقعاً غیرفعال شود.
- برای دکمه‌های فقط آیکون، `aria-label` داشته باشد.
- focus واضح داشته باشد.
- در صورت loading، وضعیت آن برای screen reader قابل تشخیص باشد.

در `Button.jsx` نسخه‌ی اولیه وجود دارد، اما در حال حاضر variantها، focus state و loading behavior بسیار محدود هستند و باید در فاز ۳ کامل شوند.

# ۳. کامپوننت Card

Card برای نمایش واحدهای مستقل اطلاعات استفاده می‌شود، مانند:

- KPI card
- اطلاعات یک کوین
- خلاصه‌ی Portfolio
- Widgetهای Dashboard
- پنل نمودار
- بخش توضیحات Coin Detail

## ویژگی‌های Card

Card باید موارد زیر را از tokenها بگیرد:

- background
- border
- radius
- padding
- shadow
- hover state در صورت تعاملی بودن

نباید رنگ‌ها یا فاصله‌ها مستقیماً در هر کامپوننت hardcode شوند.

## انواع احتمالی Card

می‌توان variantهای زیر را داشت:

- default
- elevated
- interactive
- outlined
- compact

مثلاً Card تعاملی هنگام hover باید وضعیت بصری مشخص داشته باشد، اما Card صرفاً اطلاعاتی نباید cursor یا hover غیرضروری داشته باشد.

## نکته مهم

Card نباید همیشه محل قرار دادن هر چیزی باشد. صفحه نباید به مجموعه‌ای از کارت‌های تو در تو تبدیل شود. Card برای یک واحد واقعاً مستقل مناسب است، نه برای هر بخش کوچک صفحه.

نسخه‌ی فعلی `Card.jsx` پایه‌ی مناسبی دارد، اما باید API، semantic HTML و stateهای آن دقیق‌تر شوند.

# ۴. کامپوننت Badge

Badge برای نمایش وضعیت‌های کوتاه و قابل اسکن استفاده می‌شود.

در این پروژه کاربردهای مهم آن عبارت‌اند از:

- درصد رشد
- درصد افت
- وضعیت مثبت، منفی یا خنثی
- rank یا category
- وضعیت data source
- برچسب‌هایی مانند Trending

## Variantهای اصلی

طبق Design Direction:

- `up` برای رشد
- `down` برای افت
- `neutral` برای مقدار خنثی

این رنگ‌ها باید از tokenها بیایند:

- `--color-up`
- `--color-down`
- `--color-neutral`
- رنگ‌های muted مربوط به آن‌ها

## نکات مهم

Badge نباید فقط با رنگ معنا را منتقل کند. مثلاً بهتر است مقدار مثبت با علامت `+` یا متن مناسب نیز قابل تشخیص باشد.

نمونه:

```text
+4.82%
-2.14%
0.00%
```

در `Badge.jsx` این بخش تا حدی وجود دارد، اما باید:

- type مشخص داشته باشد.
- مقدارهای نامعتبر را مدیریت کند.
- خوانایی در Light و Dark mode بررسی شود.
- در صورت نیاز aria-label مناسب داشته باشد.

# ۵. کامپوننت Tabs

Tabs در پروژه برای بخش‌هایی مانند این استفاده خواهد شد:

- All
- Top Gainers
- Top Losers
- Trending
- timeframeهای نمودار:
  - 24h
  - 7d
  - 30d
  - 1y

## رفتار مورد انتظار

Tabs باید:

- نقش `tablist` داشته باشد.
- هر گزینه نقش `tab` داشته باشد.
- tab فعال `aria-selected="true"` داشته باشد.
- به یک panel مشخص متصل باشد.
- با keyboard قابل کنترل باشد.
- focus قابل مشاهده داشته باشد.
- در موبایل overflow مناسبی داشته باشد.

## Keyboard navigation

حداقل رفتار مطلوب:

- Tab برای ورود به مجموعه‌ی Tabs
- Arrow Left و Arrow Right برای جابه‌جایی بین tabها
- Home برای رفتن به اولین tab
- End برای رفتن به آخرین tab
- Enter یا Space برای فعال‌سازی در صورت استفاده از manual activation

در `Tabs.jsx` ساختار پایه وجود دارد، اما هنوز باید keyboard navigation کامل، focus management و ارتباط دقیق با tab panel اضافه شود.

# ۶. کامپوننت Table

Table در فازهای بعدی نقش بسیار مهمی دارد، مخصوصاً در:

- Markets
- Watchlist
- Portfolio
- Compare

## اجزای موردنیاز Table

بهتر است Table به بخش‌های کوچک‌تر تقسیم شود:

- `Table`
- `TableHeader`
- `TableBody`
- `TableRow`
- `TableHead`
- `TableCell`
- در صورت نیاز `TableCaption`
- در صورت نیاز `TableEmpty`

## نیازهای بصری

Table باید داشته باشد:

- border و divider مناسب
- hover row
- selected row در صورت نیاز
- header خوانا
- اعداد با فونت tabular
- alignment درست برای عدد و متن
- horizontal scroll در موبایل
- حداقل عرض مشخص برای ستون‌ها
- وضعیت loading
- وضعیت empty
- وضعیت error

## رفتار تعاملی

در فاز ۳، لازم نیست منطق کامل sort و pagination ساخته شود؛ آن‌ها در فاز ۶ پیاده‌سازی می‌شوند. اما Table باید از ابتدا برای آن‌ها آماده باشد.

یعنی API کامپوننت نباید طوری باشد که بعداً اضافه کردن موارد زیر سخت شود:

- sortable header
- sort direction
- row click
- selectable row
- pagination
- virtualization

## دسترسی‌پذیری Table

- استفاده از semantic table واقعی
- استفاده‌ی صحیح از `<th>` و `<td>`
- مشخص بودن header هر ستون
- عدم استفاده از `<div>` به‌جای جدول در جایی که داده واقعاً tabular است
- اگر row قابل کلیک است، keyboard behavior آن باید تعریف شود
- اگر row نقش interactive دارد، نباید فقط با mouse کار کند

در `Table.jsx` نسخه‌ی پایه موجود است، اما row قابل کلیک فعلاً فقط با `onClick` کار می‌کند و نیاز به keyboard accessibility دارد.

# ۷. کامپوننت Input

Input برای موارد زیر لازم است:

- جست‌وجوی کوین‌ها
- جست‌وجو در Markets
- جست‌وجو در Compare
- ورود مقدار دارایی
- ورود قیمت خرید
- فیلترها

## قابلیت‌های لازم

Input باید پشتیبانی کند از:

- label
- placeholder
- helper text
- error message
- disabled
- readOnly
- required
- invalid state
- loading یا pending در صورت نیاز
- icon سمت چپ یا راست در صورت نیاز
- clear button برای search

## دسترسی‌پذیری

هر Input باید:

- label واقعی یا `aria-label` داشته باشد.
- در صورت خطا با `aria-invalid="true"` مشخص شود.
- به پیام خطا با `aria-describedby` متصل شود.
- پیام helper و error با هم اشتباه نشوند.
- focus واضح داشته باشد.

نمونه‌ی مفهومی:

```jsx
<Input
  label="Search coins"
  placeholder="Bitcoin, Ethereum..."
  error={errorMessage}
/>
```

در ساختار فعلی فایل جداگانه‌ای برای Input وجود ندارد؛ بنابراین این یکی از خروجی‌های اصلی فاز ۳ است.

# ۸. کامپوننت Select

Select برای گزینه‌های محدود و از پیش تعریف‌شده مناسب است.

کاربردها:

- انتخاب currency
- انتخاب sort order
- انتخاب تعداد آیتم در صفحه
- انتخاب نوع فیلتر
- انتخاب دسته‌بندی
- انتخاب تنظیمات Portfolio

## نکته مهم

برای مجموعه‌های کوتاه و دائماً قابل مشاهده، Tabs مناسب‌تر است. برای گزینه‌های زیاد یا انتخاب غیرهم‌زمان، Select مناسب است.

Select باید داشته باشد:

- label
- placeholder
- selected value
- disabled
- error
- focus state
- keyboard navigation
- aria attributes

اگر Select سفارشی با popover ساخته شود، پیچیدگی دسترسی‌پذیری آن زیاد است. در صورت نیاز بهتر است ابتدا از native `<select>` استفاده شود، مگر اینکه نیاز محصولی مشخصی برای نسخه‌ی سفارشی وجود داشته باشد.

در ساختار فعلی پروژه Select وجود ندارد.

# ۹. کامپوننت Skeleton

Skeleton برای نمایش layout موقت هنگام loading استفاده می‌شود.

در این پروژه نمونه‌های لازم شامل:

- skeleton برای KPI card
- skeleton برای ردیف جدول
- skeleton برای Coin Header
- skeleton برای نمودار
- skeleton برای لیست Watchlist
- skeleton برای widgetها

## اصول مهم

Skeleton باید:

- شکل کلی محتوای واقعی را نشان دهد.
- باعث پرش layout نشود.
- بیش از حد چشمک‌زن یا متحرک نباشد.
- در Dark و Light mode خوانا باشد.
- برای screen reader به‌صورت محتوای واقعی خوانده نشود.
- هنگام `prefers-reduced-motion` انیمیشن را کاهش دهد یا حذف کند.

در `Skeleton.jsx` نسخه‌ی ساده وجود دارد، اما بهتر است variantهای مخصوص متن، avatar، row و card اضافه شود.

# ۱۰. Empty State

Empty state زمانی نمایش داده می‌شود که خطایی رخ نداده، اما داده‌ای برای نمایش وجود ندارد.

نمونه‌ها:

- Watchlist هنوز خالی است.
- Portfolio هنوز دارایی ندارد.
- نتیجه‌ای برای جست‌وجو پیدا نشد.
- کوینی برای Compare انتخاب نشده است.
- داده‌ی تاریخی برای بازه‌ی مشخص وجود ندارد.

## اجزای Empty State

یک Empty state مناسب معمولاً شامل موارد زیر است:

- icon یا illustration ساده
- عنوان کوتاه
- توضیح واضح
- action اصلی، در صورت وجود

مثلاً:

```text
Your watchlist is empty
Add coins to track their performance here.
Browse Markets
```

## تفاوت Empty و Error

Empty یعنی درخواست موفق بوده اما داده‌ای وجود ندارد.

Error یعنی دریافت یا پردازش داده شکست خورده است.

این دو نباید یک پیام یا یک ظاهر داشته باشند.

در ساختار فعلی پروژه Empty component وجود ندارد و باید در فاز ۳ ساخته شود.

---

# ۱۱. Error State

Error state برای خطاهای قابل مشاهده‌ی کاربر لازم است، مانند:

- API در دسترس نیست.
- پاسخ CoinGecko نامعتبر است.
- اتصال اینترنت قطع شده است.
- درخواست timeout شده است.
- داده‌ی localStorage خراب است.
- کاربر باید دوباره تلاش کند.

## Error state باید شامل این موارد باشد

- توضیح ساده و غیرتکنیکی
- امکان Retry در صورت منطقی بودن
- نمایش context، مثلاً اینکه خطا مربوط به Market data است
- عدم نمایش secret، stack trace یا جزئیات داخلی
- حفظ layout تا حد ممکن
- پشتیبانی از حالت stale data در صورت وجود داده‌ی قبلی

نمونه:

```text
Market data is temporarily unavailable
We could not refresh the latest prices.
Try again
```

Error state نباید صرفاً یک `console.error` باشد؛ باید UI مشخص داشته باشد.

در ساختار فعلی پروژه Error component مشترک وجود ندارد.

---

# ۱۲. استفاده از Design Tokens

این یکی از مهم‌ترین بخش‌های فاز ۳ است.

در `tokens.css` تعدادی token تعریف شده است، از جمله:

- رنگ‌های پس‌زمینه
- رنگ‌های سطح
- border
- متن
- accent
- رنگ رشد و افت
- radius
- spacing
- typography
- shadow

کامپوننت‌های فاز ۳ باید فقط از همین tokenها استفاده کنند.

## چیزهایی که نباید hardcode شوند

نباید در کامپوننت‌ها رنگ‌هایی مانند این‌ها پراکنده شوند:

```css
#5b8def
#22c55e
#ef4444
```

همچنین نباید spacing و radius بدون دلیل در همه‌جا به‌صورت مستقل تعریف شود.

به‌جای آن باید از مواردی مانند این استفاده شود:

```css
var(--color-accent)
var(--color-up)
var(--radius-md)
var(--space-card-padding)
```

## هدف Tokenها

با tokenها باید بتوان:

- Dark mode را مدیریت کرد.
- Light mode را مدیریت کرد.
- contrast را اصلاح کرد.
- palette را در یک محل تغییر داد.
- ظاهر کل پروژه را بدون بازنویسی همه‌ی کامپوننت‌ها تغییر داد.

# ۱۳. Dark و Light Mode

طبق مشخصات پروژه:

- Dark mode حالت پیش‌فرض است.
- Light mode باید از همان ابتدا پشتیبانی شود.
- کامپوننت‌ها نباید فقط در Dark mode بررسی شوند.

هر کامپوننت باید در هر دو حالت بررسی شود:

- متن خوانا باشد.
- border قابل مشاهده باشد.
- disabled state بیش از حد محو نباشد.
- رنگ رشد و افت contrast کافی داشته باشد.
- focus ring دیده شود.
- Skeleton از background جدا باشد.
- Error و Empty state قابل تشخیص باشند.

# ۱۴. Keyboard و Focus Behavior

این بخش فقط مخصوص Button نیست و باید در تمام UI System رعایت شود.

## کنترل‌هایی که باید با keyboard کار کنند

- Button
- Tabs
- Input
- Select
- Table row در صورت clickable بودن
- دکمه‌ی افزودن به Watchlist
- دکمه‌ی حذف
- theme switcher
- modal یا popover در صورت وجود

## Focus

Focus نباید با این روش حذف شود:

```css
outline: none;
```

مگر اینکه جایگزین واضح و قابل مشاهده‌ای وجود داشته باشد.

Focus باید:

- contrast مناسب داشته باشد.
- در Dark و Light mode دیده شود.
- روی کنترل فعال مشخص باشد.
- هنگام حرکت با Tab layout را خراب نکند.

---

# ۱۵. aria و Accessibility

حداقل موارد موردنیاز:

- `aria-label` برای دکمه‌های icon-only
- `aria-selected` برای Tabs
- `aria-controls` برای اتصال tab به panel
- `aria-invalid` برای Input و Select دارای خطا
- `aria-describedby` برای اتصال input به helper یا error message
- `aria-live` برای پیام‌های dynamic در صورت نیاز
- نقش‌های صحیح برای tablist، tab و table
- label واقعی برای فرم‌ها
- کنتراست مناسب
- پشتیبانی از keyboard
- عدم انتقال معنا فقط با رنگ

نمونه‌ی نامناسب:

```text
فقط یک نقطه قرمز برای نمایش خطا
```

نمونه‌ی بهتر:

```text
Error: Unable to load market data
```

  Badge.jsx

# ۱۷. تست‌های موردنیاز فاز ۳

فاز ۳ فقط ساخت ظاهری کامپوننت‌ها نیست؛ رفتار آن‌ها هم باید تست شود.

طبق package پروژه، ابزارهای تست شامل Vitest و React Testing Library هستند.

## تست Button

- variant درست render شود.
- disabled مانع کلیک شود.
- loading مانع تعامل مجدد شود.
- class یا state مربوط به focus وجود داشته باشد.
- `aria-label` برای حالت icon-only پذیرفته شود.

## تست Tabs

- tab فعال درست مشخص شود.
- با click تغییر کند.
- `aria-selected` درست باشد.
- keyboard navigation کار کند.
- tabهای غیرفعال انتخاب نشوند.

## تست Input

- label به input متصل باشد.
- error باعث `aria-invalid` شود.
- پیام خطا render شود.
- مقدار ورودی به‌درستی تغییر کند.
- disabled behavior درست باشد.

## تست Select

- مقدار انتخاب‌شده مشخص باشد.
- گزینه‌ی جدید قابل انتخاب باشد.
- disabled و error درست رفتار کنند.

## تست Table

- header و cell صحیح render شوند.
- ردیف clickable با keyboard هم قابل استفاده باشد.
- loading و empty state قابل نمایش باشد.

## تست Empty و Error

- عنوان و توضیح درست render شوند.
- action اصلی کار کند.
- Retry قابل اجرا باشد.
- پیام‌ها با هم اشتباه نشوند.

در حال حاضر تست‌های موجود بیشتر مربوط به API و store هستند؛ برای UI primitiveها تست اختصاصی قابل توجهی دیده نمی‌شود.

# ۱۹. خروجی‌های نهایی مورد انتظار

در پایان فاز ۳ باید این خروجی‌ها وجود داشته باشند:

9. تست‌های unit و component برای رفتارهای مهم.
10. مستندسازی کوتاه نحوه‌ی استفاده از کامپوننت‌ها.

12. عدم اتصال مستقیم UI primitiveها به Zustand یا TanStack Query.
